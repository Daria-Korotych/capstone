# ADR-0006: Хеш-функція і віртуальні вузли — BLAKE2b-64, 200 vnodes на шард

Status: Accepted

**Рішення коротко:** consistent hashing ring, хеш BLAKE2b з 8-байтним дайджестом, 200 віртуальних вузлів на шард.

## Context

- Coordinator обирає шард за ключем кільця (ADR-0007). Хеш має давати той самий результат у кожному процесі й після рестарту.
- `hash mod N` при зміні N перетасовує майже всі ключі (Практика 4 §11). Кільце переносить лише частку, але за малої кількості вузлів ділить нерівно; ліки — віртуальні вузли, «десяток» на ноду (Практика 4 §12).
- Числа взято зі спайка (Практика 5 §10): 100 000 ключів YCSB `usertable\x1fuser<N>` → `docs/m2/evidence/ring/distribution.txt`.

## Options considered

**Хеш-функція**

| Варіант | Вердикт |
|---|---|
| BLAKE2b, `digest_size=8` | **Обрано**: є в stdlib (`hashlib`), стабільний між процесами, рівномірний, сам видає 8-байтний дайджест без обрізання — це і є 64-бітний простір кільця |
| Python `hash()` | Сіль випадкова на кожен процес (`PYTHONHASHSEED`), тож після рестарту coordinator шукав би ключі не там |
| MD5 / SHA-1 | Та сама швидкість і рівномірність, тож виграшу немає. Дайджест довелося б обрізати до 8 байтів, а як криптографія вони зламані, і лінтери їх позначають (bandit B324) — шум там, де криптостійкість не потрібна |
| mmh3 / xxhash | Зовнішня C-залежність заради невиміряного виграшу: BLAKE2b коштує 0.22 µs на ключ, що мізерно проти HTTP-хопу |
| `hash mod N` | Від 2 до 3 шардів переносить **66.64 %** ключів; кільце з 200 vnodes — 33.23 % в середньому (spike, C і B) |

**Кількість vnodes.** Критерій: найменше значення, за якого найбільший шард із двох тримає ≤ 55 % ключів (+5 п.п., тобто 10 % відносно рівної частки 50 %) у 95 % наборів id шардів. Один набір id — це лише одна вибірка: для `shard-1..2` значення 10 дає 54.04 %, а 100 — 55.45 % (spike, A). Тому рахуємо p95 по 100 наборах (spike, B).

| vnodes | 2 шарди, max %: mean / p95 / worst | 3 шарди, max % p95 | Перенесено 2 → 3, mean % |
|---|---|---|---|
| 1 | 75.58 / 97.30 / 99.80 | 82.64 | 33.79 |
| 10 | 59.01 / 71.04 / 82.64 | 53.49 | 34.14 |
| 50 | 53.73 / 60.26 / 61.81 | 41.31 | 33.74 |
| 100 | 52.93 / 57.39 / 61.88 | 39.55 | 33.76 |
| **200** | **51.86 / 54.60 / 56.70** | **37.00** | **33.23** |
| 500 | 51.24 / 53.27 / 54.96 | 35.80 | 33.22 |

## Decision

- `h(s) = int.from_bytes(blake2b(s, digest_size=8), "big")`.
- Id шардів у продакшені: `shard-1`, `shard-2`.
- Шард `<id>` ставить точки `h("<id>#<i>")` для `i < 200`. Власник ключа — перша точка за годинниковою стрілкою (`bisect_right`, після кінця — на початок).
- **200 vnodes:** p95 = 54.60 % ≤ 55 %, а 100 не проходить (57.39 %). Для продакшен-id `shard-1`, `shard-2`: 50.08 / 49.92 %.
- Ціна: 600 точок на 3 шарди, пошук 0.07 µs.
- «Десяток» з курсу не годиться: при 10 vnodes p95 = 71.04 %.

## Consequences

- Плюс: третій шард забирає близько третини ключів (33.23 %), а не 66.64 %.
- Мінус: зміна кільця без міграції даних робить перенесені ключі недосяжними (orphaned): дані лишаються на старому шарді, а coordinator шукає на новому. Міграція — це M5; у M2 це non-goal (`design.md`, Risks).
- Мінус: рівномірні ключі ще не означають рівномірних запитів, і гарячий ключ усе одно б'є в один шард (ADR-0007).
- Id шарда, формат точки і число 200 — частина алгоритму. Перейменування шарда чи зміна константи переносить ключі, тому значення зафіксовані в тестах кільця.
