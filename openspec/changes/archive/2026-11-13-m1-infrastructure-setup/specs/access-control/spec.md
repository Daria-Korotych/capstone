# Spec Delta: access-control

## Purpose

Показує, що реально дозволяє і забороняє роль, під якою працює сесія пісочниці, і як це з'ясовано, а також описує як код read-only доступ і роль, яку може взяти інший principal, разом із чесним записом того, що пісочниця не дає їх створити.

## ADDED Requirements

### Requirement: Session role permissions table
Документація проєкту SHALL містити таблицю «дія → дозволено/заборонено → доказ → як з'ясовано (console / CLI / simulator)» для ролі, під якою фактично працює сесія пісочниці, і називати цю роль; «LabRole» із завдання трактується як умовна назва.

#### Scenario: Actual session role is named
- **GIVEN** активна сесія пісочниці
- **WHEN** викладач відкриває документ про роль
- **THEN** документ називає роль, під якою працює сесія, і пояснює, що «LabRole» у завданні — умовна назва

#### Scenario: Every row states how it was found
- **GIVEN** таблиця дозволів у документі
- **WHEN** викладач переглядає будь-який рядок
- **THEN** рядок має посилання на збережений сирий вивід і спосіб перевірки: console, CLI або simulator

#### Scenario: A role literally named LabRole also exists
- **GIVEN** в акаунті є роль з іменем `LabRole`, відмінна від ролі сесії
- **WHEN** проведено розбір дозволів
- **THEN** документ має окремий розділ для цієї ролі

### Requirement: Attached policies are captured
Документація проєкту SHALL зберігати вміст кожної політики, прикріпленої до ролі сесії або вбудованої в неї, а якщо читання заборонене — точний текст відмови.

#### Scenario: Policies are readable
- **GIVEN** роль сесії може читати власні політики
- **WHEN** перелічено прикріплені і вбудовані політики
- **THEN** документ містить повний текст кожної з них

#### Scenario: Reading policies is denied
- **GIVEN** роль сесії не має права читати свої політики
- **WHEN** виконано спробу читання
- **THEN** документ містить точний текст `AccessDenied` замість вмісту

### Requirement: Refused identity operations are explained
Документація проєкту SHALL для кожної спроби створити IAM-користувача, групу, політику і роль записувати точний результат і, для відмови, чи її спричинив явний deny чи відсутність allow.

#### Scenario: Each identity creation is refused
- **GIVEN** активна сесія пісочниці
- **WHEN** виконано спробу створити кожне з: IAM-користувача, групу, політику, роль
- **THEN** документ для кожної з чотирьох спроб містить точний текст помилки
- **AND** для кожної вказано statement з явним deny або відсутність allow, що її дали

#### Scenario: A creation attempt unexpectedly succeeds
- **GIVEN** спроба створити пробний IAM-ресурс
- **WHEN** пісочниця її дозволяє
- **THEN** ресурс одразу видалено, а дія записана в таблиці як дозволена

### Requirement: Simulated permission checks are recorded
Документація проєкту SHALL зберігати результат симуляції політик ролі сесії для запуску інстансу, створення VPC, створення ролі, створення бакета і створення стеку.

#### Scenario: Simulator is available
- **GIVEN** роль сесії може викликати симулятор політик
- **WHEN** симульовано п'ять дій
- **THEN** документ містить результат кожної дії

#### Scenario: Simulator itself is denied
- **GIVEN** роль сесії не може викликати симулятор
- **WHEN** виконано спробу симуляції
- **THEN** документ містить точний текст відмови як результат

### Requirement: Read-only policy denies writes
Read-only політика, описана як код, SHALL не дозволяти жодної дії, що створює, змінює або видаляє ресурси.

#### Scenario: Write actions are implicitly denied
- **GIVEN** read-only політика
- **WHEN** перевірено створення VPC, запис об'єкта в бакет, створення ролі і видалення стеку
- **THEN** результат кожної перевірки — `implicitDeny`

#### Scenario: Object content is not readable
- **GIVEN** read-only політика
- **WHEN** перевірено читання вмісту об'єкта в бакеті
- **THEN** дія не дозволена, бо політика відкриває тільки метадані бакетів

#### Scenario: Simulator unavailable in sandbox
- **GIVEN** симуляція власної політики заборонена пісочницею
- **WHEN** запущено перевірку політики
- **THEN** відмову симулятора збережено як доказ
- **AND** статична перевірка підтверджує, що жодна дія в політиці не є записом

### Requirement: Read-only policy allows inspection
Read-only політика SHALL дозволяти дії перегляду для мережі й обчислень, стеків, метаданих бакетів, моніторингу і квот сервісів.

#### Scenario: View actions are allowed
- **GIVEN** read-only політика
- **WHEN** перевірено перегляд VPC і перегляд стеку проєкту
- **THEN** результат кожної перевірки — `allowed`

### Requirement: Resource scope is as narrow as AWS allows
Read-only політика SHALL обмежувати дії перегляду ресурсами проєкту там, де AWS підтримує обмеження за ресурсом, і лишати область «усі ресурси» тільки для дій List/Describe без такої підтримки, з поясненням поруч із цим правилом.

#### Scenario: Reviewer reads the wildcard rule
- **GIVEN** опис політики як код
- **WHEN** викладач знаходить правило з областю «усі ресурси»
- **THEN** це правило містить тільки дії List/Describe, для яких AWS не підтримує обмеження за ресурсом
- **AND** поруч є пояснення, чому інакше не можна

#### Scenario: Metadata of a non-project resource is not readable
- **GIVEN** read-only політика
- **WHEN** перевірено читання метаданих бакета або опису стеку, що не належать проєкту
- **THEN** результат — `implicitDeny`, бо ці дії обмежені ресурсами проєкту

### Requirement: Assumable role trusts a supplied principal
Опис доступу як код SHALL визначати роль із read-only політикою, яку може взяти тільки principal, переданий параметром під час розгортання.

#### Scenario: Definition passes validation
- **GIVEN** опис політики і ролі як код
- **WHEN** його перевірено валідатором AWS
- **THEN** валідація проходить без помилок
- **AND** trust policy ролі посилається на переданий principal і дозволяє тільки взяття ролі

### Requirement: Sandbox refusal is recorded, not hidden
Документація проєкту SHALL зберігати точну причину відмови пісочниці створити стек доступу і обмеження ролі сесії, яке її спричинило, і не подавати цей стек як задеплоєний.

#### Scenario: Sandbox refuses the IAM stack
- **GIVEN** валідний опис політики і ролі
- **WHEN** виконано спробу створити стек у пісочниці
- **THEN** стек падає, а точний текст причини збою збережено в документі разом із поясненням
- **AND** стек, що впав, видалено

#### Scenario: Sandbox unexpectedly accepts the IAM stack
- **GIVEN** валідний опис політики і ролі
- **WHEN** пісочниця створює стек
- **THEN** це записано як факт, стек видалено, а документ пояснює, що це означає для моделі доступу пісочниці

### Requirement: Role purpose in a regular account is explained
README проєкту SHALL пояснювати, хто в звичайному акаунті бере цю роль, що він отримує і чому роль краща за групу користувачів.

#### Scenario: Tutor asks roles versus groups
- **GIVEN** README проєкту
- **WHEN** викладач ставить контрольне питання 4 (ролі проти груп)
- **THEN** README містить відповідь: хто бере роль через `sts:AssumeRole`, які дозволи отримує і чому тимчасові креденшели ролі кращі за постійне членство в групі
