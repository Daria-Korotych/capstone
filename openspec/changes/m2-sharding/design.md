# Design: M2 — Sharding the load

## Context

Мотивація — у `proposal.md` (Why). Тут тільки обмеження й рішення.

- **Середовище:** те саме Sandbox Environment, що в M1, регіон `us-east-1` (`scripts/env.sh`); креденшели тимчасові. Власні IAM-ресурси створювати не можна, тому CI не може отримати роль через OIDC (див. ADR-0009).
- **Мережа:** стек `kv-network` з M1; `kv-app` імпортує `kv-network-VpcId` і `kv-network-PublicSubnet1Id` (підмережа `kv-dev-public-1`).
- **Вимога курсу:** ADR про протокол API, хеш-функцію з кількістю віртуальних вузлів і стратегію партиційного ключа; спека й ADR раніше за код.

## Goals / Non-Goals

**Goals:**

- Один контракт `api/openapi.yaml`, який реалізує coordinator і який перевіряється валідатором і тестами контракту.
- Розподіл ключів між шардами рівномірний у межах виміряного допуску, а додавання шарда переносить на нього лише частку ключів (властивість consistent hashing), що перевіряється тестом.
- Відтворюваний бенчмарк: умови прогону записані разом з числами.

**Non-Goals:** див. `proposal.md` (Non-goals); тут не дублюються.

## Decisions

| Рішення | Вибір | Відкинуто | ADR |
|---|---|---|---|
| Протокол і формат API | REST + JSON, контракт OpenAPI 3.1 | gRPC (потрібен клієнт-генератор у YCSB і складніше дебажити curl'ом), GraphQL (довільні вибірки полів не потрібні: кожна операція йде за ключем) | ADR-0005 |
| Хеш-функція і віртуальні вузли | BLAKE2b з 64-бітним дайджестом, кільце з віртуальними вузлами; кількість обирається експериментом (розкид навантаження проти розміру кільця) | MD5/SHA-1 (застарілі без потреби), Python `hash()` (не стабільний між процесами), модульний хеш `hash % N` (переносить майже всі ключі при зміні N) | ADR-0006 |
| Ключ кільця | таблиця + partition key; sort key не хешується, живе в межах партиції на одному шарді | хеш повного ключа з sort key (розкидає одну партицію по шардах, а діапазонні запити в майбутньому стають неможливі) | ADR-0007 |
| Стек застосунку | Python 3.12 + FastAPI, один Docker-образ із ролями `coordinator` і `shard` (обирається змінною середовища) | окремі образи (подвоює збірку без вигоди), Go/Java (довша розробка при тому самому висновку курсу) | без ADR (контекст — у ADR-0005) |
| Топологія і безпека | 3 × t3.micro у public підмережі `kv-dev-public-1` з публічними IP; Security Group шардів приймає лише від SG coordinator; coordinator `8080` — від SG шардів, `OperatorCidr` і `CiCidr` | private підмережі + NAT (платний щогодини, ADR-0004 M1), ALB (поза обсягом M2) | ADR-0008 |
| CI/CD | GitHub Actions + GHCR; образ тегується SHA коміту; деплой = оновлення CloudFormation-стеку з новим тегом, що замінює інстанси | ECR (інстанс без instance profile не автентифікується до приватного ECR, а роль не створити), CodePipeline (потрібна service role), SSH-деплой (не відтворюваний) | ADR-0009 |
| Бенчмарк | YCSB із власним Java binding до REST API; workloads A (50/50 читання/оновлення) і C (100% читання) | вбудований HTTP-binding (не мапить таблицю й sort key), workload B/D/E/F (E потребує scan, поза обсягом) | не обов'язковий ADR; обґрунтування — у контрольному питанні 8 |

### Decision: Реєстрація шардів

Шард при старті викликає `POST /shards {id, url}` у coordinator за його приватною IP (SG coordinator пускає 8080 від SG шардів, ADR-0008), передає у `url` свою приватну IP і повторює виклик кожні 15 с як heartbeat. Повторна реєстрація того самого `id` з тим самим `url` повертає 200 без змін, з іншим `url` — оновлює адресу (200). `DELETE /shards/{id}` прибирає шард із кільця лише до його наступного heartbeat: живий шард перереєструється за ≤15 с, тож видалення тривке тільки для зупиненого шарда. Coordinator сам шарди не опитує і failover у M2 немає.

### Decision: Режими coordinator (`KV_MODE`)

Режим coordinator фіксується при старті змінною середовища `KV_MODE=single|sharded` (за замовчуванням `sharded`); автоматичного переходу між режимами немає. У режимі `single` coordinator зберігає дані локально й ігнорує кільце та реєстрацію шардів (завдання 2). У режимі `sharded` усі записи йдуть через кільце; з порожнім кільцем coordinator повертає 503. `GET /health` повертає `{status, mode, shards}`.

### Decision: Креденшели CI

Тимчасові креденшели пісочниці (access key, secret, session token) копіюються в GitHub Actions secrets `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` скриптом `scripts/push-session-creds.sh` на початку кожної сесії пісочниці. Той самий скрипт виставляє GitHub variable `OPERATOR_CIDR` (поточна IP оператора `/32`) для параметра стеку `OperatorCidr`. Перший крок deploy-job — `aws sts get-caller-identity`; якщо креденшели протухли, job падає з чітким повідомленням. OIDC і CodePipeline відкинуто: пісочниця забороняє `iam:CreateRole` (ADR-0009).

### Decision: Помилки шардів

Недоступний шард → 502 з тілом `{error, detail?, shard}`. 503 — коли немає жодного шарда для sharded режиму (кільце порожнє після `DELETE`) або coordinator не готовий. Retries немає (поза обсягом).

### Decision: Ключі і таблиці

Ім'я таблиці за шаблоном `^[A-Za-z0-9_-]{1,64}$`; значення ключів — рядки. `sk` потрібен тоді й лише тоді, коли таблиця має `sort_key`. Таблиці зберігає coordinator (метадані), записи — шарди.

### Відповідність вимог реалізації

|---|---|---|

## Risks / Trade-offs

- [Зміна кільця втрачає доступ до ключів] → задокументовано як non-goal; тест фіксує, яка частка ключів змінює власника.
- [Публічні IP шардів] → Security Group шардів лише від SG coordinator; порт 8080 coordinator — від SG шардів (реєстрація і heartbeat на приватну IP), з `OperatorCidr` (обов'язковий параметр без значення за замовчуванням: локальний деплой-скрипт передає `/32` того, хто викликає, CI читає GitHub variable `OPERATOR_CIDR`, яку виставляє `scripts/push-session-creds.sh`) і з `CiCidr` (необов'язковий; deploy-job передає `/32` раннера для smoke-тесту); 8081 шарда — лише від SG coordinator; API без автентифікації (non-goal), тож відкритий для цих CIDR порт coordinator — прийнятий ризик навчального середовища.
- [t3.micro: CPU credits закінчуються під навантаженням] → прогін YCSB записує режим кредитів; тривалі прогони не змішуються з тестом на довжину.
- [Дані в пам'яті втрачаються при заміні інстанса під час деплою] → очікувано до M3; пайплайн не гарантує збереження даних.
- [Heartbeat без перевірки живості] → шард, що впав, лишається в кільці, запити до нього дають 502; після зупинки шарда його прибирають через `DELETE /shards/{id}`; видалення тривке, бо heartbeat більше не приходить.
- [Сесія пісочниці протухла посеред деплою] → `scripts/check-session.sh` лишається першим кроком деплой-скриптів, як у M1.
